# HTML 交付 / 预览稿写法

本文件只用于在用户明确要求 HTML 最终稿或网页阅读稿时，生成 `report.html` 或按任务语义命名的 `xxx.html`。

## 一、什么时候才用 HTML

只有满足以下条件之一时，才使用 HTML：

- 用户明确要求 HTML 最终稿
- 用户明确要求网页阅读稿
- 需要临时浏览器预览，而其他正式稿稍后再生成

不要把 HTML 当默认交付物；只有在用户明确要 HTML 时才生成。

## 二、推荐页面结构

推荐使用以下结构：

1. 标题区
2. 摘要
3. 关键词
4. 研究范围与方法
5. 主体分析
6. 争议、局限与适用边界
7. 结论
8. 参考文献

如需附加说明，可增加：

- `研究对象与样本`
- `术语说明`
- `附录`

## 三、正文组织

- 每个一级 section 只回答一个明确问题
- 每个段落都应能回答“这段为什么存在”
- 通用背景压缩到最少，主体篇幅留给真正需要比较、核验和解释的内容
- 如果证据不足，不要靠“未来趋势”“行业共识”“广泛应用”凑字数

## 四、引用写法

正文中的引用建议使用编号锚点：

```html
<p>
  某项结论的正文表述
  <sup class="citation"><a href="#ref-3">[3]</a></sup>
</p>
```

参考文献区建议写成：

```html
<ol class="references">
  <li id="ref-3">机构名. 标题. 年份. 链接或出处.</li>
</ol>
```

规则：

- 一个关键判断至少对应一个明确引用
- 多个来源共同支撑同一判断时，可并列多个编号
- 缺作者、DOI、页码时允许留空，但不能猜

## 五、学术排版建议

- 正文优先用衬线字体栈，标题和元信息可用无衬线字体栈
- 控制行宽，正文容器建议 760px 到 900px
- 行高保持 1.7 到 1.95
- 大标题与正文拉开明显留白
- 优先采用白底、细分隔线、期刊式层级，不要做成海报页、产品页或 dashboard
- 表格仅用于字段型比较，不要把整篇报告写成表格堆叠
- 如果任务是文献综述或学术综述，版式应接近期刊文章，而不是咨询报告或品牌白皮书

## 六、打印与导出兼容

- 使用完整 HTML 文档，而不是片段
- CSS 写在 `<style>` 内，避免外链
- 尽量不用 JavaScript
- 尽量使用扁平 CSS 和语义标签，方便后续导出 `.docx`
- 图片如非必须，可不使用；若使用，优先本地可访问路径或内联资源

## 七、分段写入协议

只有在确实生成 HTML 预览稿时，才按以下方式分段写入，不要一次性生成整篇 HTML。推荐顺序：

1. 第一次写入：
   - 文档头部
   - `<style>`
   - 标题区
   - 打开的主体容器，例如 `<main>` 或 `<article>` 内层容器
2. 中间多次追加：
   - 摘要
   - 方法
   - 每个主体分析 section
   - 局限 / 争议
   - 结论
3. 最后一次追加：
   - 参考文献
   - 页脚
   - closing tags

执行规则：

- 单次只写一个一级 section，或最多两个非常短的小 section
- 每次追加前先确认上一段已经稳定，不要把整篇 HTML 重新生成一遍
- 如需修改某一节，优先做局部编辑，不要整篇覆盖
- 这样做的目的是降低长输出时的质量衰减和网关等待超时风险

## 八、模板使用边界

- 模板只提供版式骨架，不提供固定内容结构
- 最终 section 应根据任务裁剪，不要为了“看起来完整”硬塞摘要、方法、讨论、附录
- 文献综述优先使用“引言 -> 文献分组综述 -> 讨论 -> 结论 -> 参考文献”
- 专题报告才更适合“目标/方法/分析/建议”这类结构
- 如果模板风格与用户任务不匹配，应以任务类型为准修改骨架，而不是强行贴模板

## 九、低质量表现

以下现象通常说明 HTML 只是“把 Markdown 包了一层壳”：

- 把 Markdown 原样塞进 `<pre>` 或 `<p>`
- 标题很多，但每节都只有空泛定义
- 有参考文献列表，但正文没有对应引用锚点
- 段落只重复“重要、显著、广泛、快速发展”等抽象判断
- 大量列表，没有连续论证
