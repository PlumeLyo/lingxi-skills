# 深度研究交付前闸门

在交付正式稿前，必须逐项检查。只要有一项明显不满足，就先修改，不要急着交付。

## 一、研究问题是否真正被回答

- 标题、摘要、正文和结论是否在回答同一个问题
- 是否把篇幅主要放在用户真正关心的部分，而不是通用背景
- 结论是否正面回答了研究问题，而不是只做“本文介绍了……”式总结

## 二、关键判断是否有证据

- 每个关键判断能否在 `evidence-ledger.md` 中找到对应记录
- 精确数字、比例、排名、时间点是否都有明确出处
- 如果来源之间有冲突，正文是否解释了冲突原因
- 如果证据不足，是否已经改成保守表述

## 三、是否存在“写起来很像真的”空话

重点删除或改写以下句子：

- “广泛应用”“显著提升”“效果明显”“行业普遍认为”
- “某头部企业内部数据显示”
- “未来将全面普及”“预计将达到”

替换方向：

- 写成可回查的事实
- 写成带边界的判断
- 写成来源之间的比较

## 四、论证是否连续

- 每节是否都有明确中心问题
- 段落是否遵循“观点句 -> 证据 -> 分析 -> 过渡”
- 是否只是堆资料、堆案例、堆列表，而没有解释差异和意义

## 五、交付物是否真的可交付

- 最终交付路径是否与用户要求一致：`docx / pptx / pdf / xlsx / html / 无文件`
- 最终文件是否已经生成，且文件名符合任务主题与交付类型语义
- 如果最终交付是 `.docx`：结构、样式与目录层级是否完整
- 如果最终交付是 `.pptx`：页级故事线、标题、关键图表或结论页是否完整
- 如果最终交付是 `.pdf`：文件是否可打开、分页是否正常、正文是否可读
- 如果最终交付是 `.xlsx` / `.csv`：字段、表头、工作表结构、公式或图表是否完整
- 如果最终交付是 `html`：正文引用是否能跳到参考文献条目，文件是否为完整 HTML，而不是 Markdown 换皮

## 六、最终判定

只有同时满足以下条件，才可以交付：

- 研究问题已被正面回答
- 关键判断都可回查
- 争议和局限没有被跳过
- 没有明显的空话和可疑数字
- 最终交付物已经生成、格式正确、命名合理，且不是机械的 `report.*`
