# 深度研究

把"搜资料"变成"有证据约束的研究写作"。先界定问题，再检索与核验；先整理证据台账，再写正文。目标不是堆字数，而是让结论可回查、可复核、可交付。`deep_research` 默认负责"研究过程"，最终交付载体再按任务语义分流。

默认按以下顺序工作：

- 先定义研究问题，再制定检索框架
- 先做宽搜，再对关键判断定向核验
- 先整理 `evidence-ledger.md`，再生成正文
- 最终交付物按任务语义做路径分流

> **依赖与分流**
>
> - 当前环境有 `search` 和 `url_fetch` 时，优先用它们完成检索与正文抓取。
> - 需要处理动态网页、JavaScript 页面、搜索摘要不足或必须核对原网页最新内容时，先阅读 `skills/browser/SKILL.md`，再使用 browser。
> - 先阅读 `references/deliverable-routing.md`，判断最终交付属于聊天内结论、HTML，还是需要切换到 `docx / pptx / pdf / xlsx / wps` 等现有 skill。
> - 若最终交付是普通 Word 报告，切换到 `skills/docx/SKILL.md`；若是 PPT，切换到 `skills/pptx/SKILL.md`；若是 PDF，切换到 `skills/pdf/SKILL.md`；若是表格或数据清单，切换到 `skills/xlsx/SKILL.md`。
> - 只有用户明确要求 HTML 最终稿或网页预览稿时，才生成 `report.html`；不要把 HTML 当默认交付物。

## 默认沉淀物与交付路径

正式任务默认沉淀以下研究中间件：

- `research-plan.md`：研究问题、研究维度、关键词与执行顺序
- `evidence-ledger.md`：关键结论、来源、日期、证据摘录、冲突与置信度

按最终交付路径，再补充以下文件：

- HTML：按任务语义命名的 `xxx.html` 或 `report.html`
- 通用 Word / PPT / PDF / 表格：研究完成后切换到对应 skill，再生成 `xxx.docx` / `xxx.pptx` / `xxx.pdf` / `xxx.xlsx` / `xxx.csv`

开始正式研究任务时，优先读取并复用以下通用模板：

- `assets/research-plan-template.md`
- `assets/evidence-ledger-template.md`

小任务或用户只要聊天内结论时，可以不落盘，但仍要遵守同样的证据标准。

## 核心原则

1. **问题驱动，不是资料驱动**：先确定要回答什么，再决定搜什么。
2. **原始来源优先**：优先官方文档、论文、标准、财报、监管披露、原始数据。
3. **关键结论必须能定位到来源**：正文里的每个重要判断都要能在 `evidence-ledger.md` 里找到支撑。
4. **只对关键判断做二次核验**：不是每段都强行"两轮研究"，而是对数字、排名、因果、争议点做重点复核。
5. **通用背景压缩**：用户研究的是某个具体问题时，教科书式背景通常不应超过全文的 15%-20%。
6. **宁可少写，也不要补空话**：证据薄弱就缩短该节，不要用行业套话填篇幅。

## 工作流

### 第 0 步：先做交付路径分流

进入本技能后，先阅读 `references/deliverable-routing.md`，再判断最终交付属于哪一类：

- **聊天内结论 / 无文件路径**：
  用户只要研究结论、对比、建议，不要求落盘时，直接在聊天内交付，不强制生成文件。
- **HTML 路径**：
  只有当用户明确要求网页阅读稿、HTML 最终稿或浏览器预览稿时，才继续留在本技能内生成 HTML。
- **外部包装 skill 路径**：
  如果最终交付是普通 Word 报告、PPT、PDF、表格或 WPS 云文档，先在本技能中完成研究与内容整理，再切换到对应 skill 做最终包装。不要在本技能内重写 PPT / PDF / XLSX 的生成细节。

如果用户需求同时包含"要做深度研究"与"最后导出普通报告 Word / PPT / PDF / 表格"，也先在本技能中完成研究，再把最终包装交给对应 skill，不要混成一条链。

### 第 1 步：界定研究任务

如果用户目标还不清楚，最多补 3 个关键问题，优先问：

- 最终要解决什么问题
- 输出更偏"决策报告"还是"专题分析"
- 是否限定时间、地区、行业、对象、语言或来源类型

如果用户已经讲清楚，就直接进入下一步，不要为了提问而提问。

### 第 2 步：先做研究框架

先把主题拆成 3-6 个研究维度，并为每个维度写清：

- 核心问题
- 需要的来源类型
- 可能的中英文关键词变体
- 本维度需要产出的判断

对于"对象枚举型"任务，例如调研一批产品、论文、模型、公司、政策案例，先列出：

- 研究对象清单
- 每个对象需要采集的字段
- 哪些字段必须有来源支撑

如果任务规模较大，可先给出"研究框架 + 执行顺序"，再分批深入。不要在计划阶段写冗长方法学宣言。

### 第 3 步：资料获取顺序

#### A. 优先使用当前环境能力

1. 先用 `search`
2. 再用 `url_fetch` 读取关键页面全文
3. 动态页、需交互、需核对最新页面内容时，再使用 `browser`

#### B. `search` 类型选择

- 学术论文、白皮书、政府 / 行业报告：`type="research"`
- 官网说明、产品文档、事实性资料：`type="info"`
- 近期动态、时效性事件、发布消息：`type="news"`
- 公开统计、数据源、榜单、数据库：`type="data"`

#### C. 搜索要求

- 每次搜索只围绕一个意图，最多 3 个 query 变体
- 中文查询时，最后一个 query 尽量提供英文变体，扩大覆盖面
- 不要只看搜索摘要；关键来源必须继续抓全文
- 复杂课题必须分步搜索，不要把所有条件塞进一个超长 query
- 对关键数字、排名、市场份额、实验结果、发布日期，必须抓到原文或接近原文的页面

#### D. browser 兜底规则

以下情况必须切到 browser：

- `url_fetch` 拿不到有效正文
- 页面强依赖 JavaScript
- 搜索结果与原网页发布时间、标题、数据不一致
- 需要翻页、点开 tab、下载文件或查看页面隐藏内容

来源优先级与场景化来源选择详见 `references/source-priority.md`。

### 第 4 步：建立证据台账

在写正文前，先整理 `evidence-ledger.md`。建议每条至少包含：

- 结论或待判断的问题
- 来源标题
- 来源类型
- 作者 / 机构
- 发布时间或更新时间
- 能支撑该结论的原句、数据或事实
- 是否存在冲突来源
- 当前置信度：`已证实` / `较可信` / `待验证` / `无法判断`

正文只允许使用台账里已经记录过的关键判断。不要边写边编。

如果是正式交付件：

- 先用 `write_file` 创建 `research-plan.md`
- 再用 `write_file` 创建 `evidence-ledger.md`
- 如使用 HTML 路径，再生成按任务语义命名的 `xxx.html` 或 `report.html`
- 如最终交付是普通 Word / PPT / PDF / 表格，则在本技能内完成研究与结构整理后，切换到对应 skill 生成最终文件

### 第 5 步：对关键判断定向核验

以下内容必须优先做二次核验：

- 精确数字、增长率、准确率、市场份额、效率提升
- "行业第一""主流""广泛采用"等带比较含义的表述
- 带时间敏感性的政策、产品版本、组织数量、融资或财务数据
- 明显会影响结论方向的争议点

如果二次核验做不到：

- 删除该数字或改写成保守的定性判断
- 明确标注"待验证"或"无法确认"
- 不要为了显得专业而保留可疑百分比

### 第 6 步：综合分析

跨主题综合时，必须处理四件事：

1. 把不同来源放到同一语境下比较
2. 解释一致之处和冲突之处
3. 区分事实、解释、推测和建议
4. 说明结论的适用边界、局限与时间敏感性

如果任务是"比较不同对象"，不要只做并列表格；还要说明造成差异的原因，以及这些差异意味着什么。

## 反空话约束

以下写法默认视为低质量，除非台账里有明确证据：

- "近年来得到了广泛关注和应用"
- "某头部机构 / 某业内公司内部测试显示"
- "显著提升效率""大幅降低成本""效果显著优于"
- "未来将全面普及""预计将达到"

对这类句子，优先改成以下三类表达：

- **事实句**：谁在什么时候发布了什么、做了什么
- **比较句**：不同来源在哪些口径上得出不同结论
- **限定句**：这个判断只适用于什么场景、时间窗口或样本范围

## 写作规则

- 主体段落优先使用"观点句 -> 证据 -> 分析 -> 过渡"的结构
- 不要把文献逐条罗列；要按主题、方法、结论或争议组织
- 任何精确数字都要能回溯到来源；如果缺出处，就删掉
- 不能把搜索摘要、营销文案或媒体转述当作最终证据
- 如果一个小节只有共识性常识，没有新的研究发现，就缩短或合并
- 如果用户研究的是行业落地，不要把主体篇幅浪费在通用技术原理介绍上
- 对关键来源说明其性质：原始研究、综述、官方说明、行业报告、媒体报道等
- 如果用户没有指定格式，默认使用可回查的编号引用；若指定 APA、GB/T 7714，再统一整理

## HTML 交付或预览（仅显式要求时）

只有当用户明确要求 HTML 最终稿或网页预览稿时，才输出 `report.html` 或按任务语义命名的 `xxx.html`。

此时：

- 先阅读 `references/html-report.md`
- 再阅读 `references/final-gate.md`
- HTML 只在用户明确要 HTML 时生成；不要把 HTML 当默认交付物

## 质量门槛

提交前至少自检以下问题：

- 是否存在无来源的关键结论
- 是否存在无出处的精确数字或排名
- 是否过度依赖单一网站或单一立场
- 是否核对了关键数字、日期、名称、版本
- 是否单独说明了争议点与不确定性
- 是否把搜索摘要误当成最终证据
- 是否把"趋势判断"写成了"已证实事实"
- 若额外生成了 `report.html`，其正文引用是否都能跳转到参考文献条目

提交前必须再阅读一次 `references/final-gate.md`。若未通过，先重写再交付。
